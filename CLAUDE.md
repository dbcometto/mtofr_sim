# MTOFR_SIM

Simulator for platform-agnostic mission-type orders. Pure Python (numpy/scipy/matplotlib), no ROS/networking/async libs yet.

## Architecture (see `notes.md` for full history/rationale)

Per-platform layers, redesigned as fully peer-to-peer/mesh (see `notes.md`'s 19 Aug 26 entry for the full rationale; supersedes the earlier centralized Foreman/Relay/Frontend design and the four-relay/MissionBuilder sketch that followed it — neither was built, both are marked superseded in `notes.md` rather than deleted):

- **Backseater** (`backseater/backseater.py`) — platform-agnostic. Holds the mission graph, relays typed capability requests to its Frontseater, never touches physical state. Exposes `capabilities()` as a passthrough to its Frontseater's registry — the real query path a planner uses instead of assuming what a platform can do. Exposes `status()` as a read-only snapshot (active node, blocked flag, per-primitive capability/status/inputs — the static `field_name -> knowledge_key` mapping from the mission graph, not a live-resolved value). `Backseater` owns platform identity exactly as before: an optional `platform_id: str` given at construction cascades to `self.frontseater.platform_id` — the one place identity is set. `Backseater` also owns an optional `clock: Clock`, now stamping every write across all four databases below (not just Knowledge).

  **Four separate databases per platform, all owned by Backseater:**
  - **Knowledge** (`knowledge/knowledge.py`) — arbitrary entry keys (not platform_id-keyed), strongly typed via `declare()`/`declare_key()`. Declaration is now callable by a Frontseater/capability at any time, not only seeded once from the mission graph's `"knowledge"` section at construction — ordinary type/existence checking still applies on every write.
  - **Mission** — keyed by platform_id, one `mission_graph` value per platform. A write must pass, at the single Backseater write point: a privilege check (see below), a type check, and a structural verify (every edge-condition key referenced in the graph must be declared in that graph's own `"knowledge"` section — edge-reachability checking still deferred). A successful write triggers hot-swap (see below).
  - **Capabilities** — keyed by platform_id, one value per platform, self-write-only: a gossiped snapshot of that platform's own `CapabilityRegistry`.
  - **Status** — keyed by platform_id, one value per platform, self-write-only: a combined status + arbitrary free-text message a capability can write, gossiped across the mesh like the others so an operator/LLM can observe a remote platform's health or errors without local access — this is what actually travels now, replacing the old local-only `status()` concept as the cross-platform-visible piece.

  A running capability is no longer resolve-then-execute: while active it can `query()`/`write()` (or declare a brand-new key) through its Backseater at any time, against any of the four databases above, instead of only receiving resolved input values once at start. Backseater remains the sole thing enabling/disabling capabilities; Frontseater remains the sole thing executing them — this relationship is unchanged, just richer in its data flow. Backseater still enforces every type check before a query resolves or a write is accepted, keeping type-safety centralized rather than left to each Frontseater implementation to check for itself.

  Every entry across all four databases carries an `origin_platform_id` — the platform that held it at its most recently locally-converted timestamp, transitively — alongside its value/timestamp; this is what privilege checks key off of.

  **Privilege hierarchy**: each platform is assigned an integer privilege level (0 = highest) by the simulation harness at construction — a deliberate placeholder, not real security, not modeling an adversarial actor. A platform may write another platform's Mission database, or reassign another platform's privilege level, only if its own level is strictly higher-privilege (lower number) than the target's; it may only assign levels less-or-equal to its own, and can never modify its own level.

  **Hot-swap**: when a Backseater detects its own Mission database entry has changed, it declares/sets every knowledge key listed in the new graph's `"knowledge"` section, cancels every currently-running capability from the old graph, sets the active node to the new graph's declared start node, and starts that node's capabilities.

  All type/privilege/structural checks happen write-side only, once, at the originating platform's `publish()` call — there is no receipt-side re-verification; the network is assumed correct downstream of a valid write.

- **Frontseater** (e.g. `world/ground_plane/frontseater.py`) — platform-specific planning/control brain (MPC, capability implementations). Talks to its Hardware only through `send_controls`/`read_state`. Builds its own `CapabilityRegistry` declaratively in `__init__` and returns it from `capabilities()` — there is no separate central capability manifest; a planner learns what a platform can do only by querying that platform's own backseater. Implements `start_capability()`/`poll_status()`/`cancel()`; a capability now calls `query()`/`publish()` on its own Backseater whenever it actually needs data, for any of the four databases, rather than only being handed resolved input values at start; `poll_status()` still returns `{"status": ..., "outputs": {name: value, ...}}` for whatever a capability decides is meaningful to report on a given status. `Frontseater.platform_id` is a property whose setter also assigns `self.hardware.platform_id`, cascading a Backseater-assigned id all the way down to Hardware automatically.
- **Hardware** (e.g. `world/ground_plane/hardware.py`) — unchanged by this redesign: MCU/actuator-equivalent, owns `WorldState`, pure `calculate_dynamics`, `read_state()` through a `PerfectSensor` stub, holds a plain `platform_id: str | None` attribute set only via the Frontseater cascade.

There is no centralized Relay. `World` drives the mesh sync itself — since it's the one thing already holding every platform's Backseater — rather than delegating to a separate Relay object. `World` ticks: `backseater.update()` → `frontseater.update()` → `environment.step_dynamics_all(hardware)` → a pairwise mesh sync between every pair of Backseaters (full connectivity assumed for now; real comms topology/partial connectivity explicitly deferred). World owns *who can currently talk to whom*; Backseater owns *what a sync actually does* once two platforms are paired, via a `sync_with()`-style method absorbing what the old Relay class used to do: pulling/pushing all four databases, last-write-wins by (locally-converted) timestamp — a named simplification, not a robust consensus mechanism. `World` itself remains platform-count-agnostic, and so does the viz layer (`MissionDashboard`'s platform dropdown and `PlanePlotter`'s per-entity rendering both iterate `world.backseaters`/`world.get_states()`); adding another platform is still purely a matter of building another independent hardware/frontseater/backseater stack and adding it to the `backseaters` dict, with no shared state required between stacks beyond what mesh sync itself provides. Cross-platform *coordination* (cross-graph reasoning) remains out of scope for Backseater/Frontseater — only cross-graph *inspection* belongs in a future planner/visualizer — but cross-platform *data propagation* is now peer-to-peer rather than routed through a central component.

Clock (`clock/clock.py`) is repurposed rather than dropped: still owned by Backseater, but instead of one global offset reset to 0.0 by a central Relay, each pairwise `sync_with()` handshake estimates a clock offset to that specific peer, and every incoming fact's timestamp is converted into the receiving platform's own local clock frame immediately and re-stamped in local time before storage — there is no shared/authoritative clock anywhere.

Default startup mission: every platform starts on a hardcoded default mission graph at init (e.g. an idle/loiter loop for an ordinary platform). An eventual LLM/operator "interface" platform (architecturally just another platform, no special class, with a single node running all its own capabilities concurrently under an unconditional self-transition) and any mission-authoring surface for building/editing a graph before publishing it (an interactive capability/Frontseater, replacing the earlier MissionBuilder sketch) are explicitly **deferred to a future step** — not part of this redesign.

Mission graph shape: `{"knowledge": {key: {"type": type, "value": value}, ...}, "nodes": {id: {"primitives": {name: {"capability", "inputs", "outputs"}}}}, "edges": {id: [{"condition": [token, ...], "to": ...}]}, "start": id}`, unchanged in shape by this redesign. The top-level `"knowledge"` section declares every Knowledge key the graph uses (type-locked, seeded with a default `value`) — Backseater seeds `Knowledge` from it both at construction (the hardcoded default mission) and on every subsequent hot-swap (a new value written to that platform's Mission database entry). A primitive's `"inputs"`/`"outputs"` dicts map a capability's declared field names to Knowledge keys (never raw literals — see Capability registry below); with a running capability now able to `query()`/`publish()` at will, these static maps are the *initial* binding a mission graph hands a capability, not the only data it will ever see. `"condition"` is a pre-tokenized boolean expression over Knowledge keys (see Condition below). Multiple primitives can be concurrently active *within* one node; only one node is active at a time (not yet a true concurrent automaton — see build order). `missions.py` holds `main.py`'s example mission graph dicts, named `mission_<set>_<platform_id>`, grouped by an exported `MissionSet` IntEnum and imported rather than inlined, so `main.py` stays wiring-only.

**Capability registry** (`capability/capability.py`): `ParamSpec` is downgraded by this redesign to carry just a key name plus a declared type (plus plaintext description) — used only for `capabilities()`'s self-description (so a human or LLM can understand what a capability needs by reading its description), no longer used for eager value-resolution. `Capability` (`ipl_type`, description, `inputs`, `outputs`, `describe()`) + `CapabilityRegistry` (keyed by `ipl_type`; `.get()`, `.all()`, `.describe()`). A primitive's `"capability"` field in the mission graph must match a `Capability.ipl_type`, and that same string is what gets passed straight through to `Frontseater.start_capability()` — no separate internal capability name. `ParamSpec.describe()` calls `type.describe()` when `type` is a `KnowledgeEntry` subclass (duck-typed via `hasattr`), and omits it for plain types (`float`, `bool`, ...) which don't implement that contract. A capability is handed keys, not resolved values, and calls `query()`/`publish()` on its own Backseater whenever it actually needs data, against any of the four databases — Backseater still enforces that the key's declared type matches the matching `ParamSpec` before a query resolves or a publish is accepted, keeping type-safety centralized rather than left to each Frontseater implementation.

**Knowledge** (`knowledge/knowledge.py`): `Knowledge` is a typed, type-locked key -> value store (one instance per backseater, exposed as `backseater.knowledge`) — one of Backseater's four databases (see architecture above; Mission/Capabilities/Status are platform_id-keyed siblings). Every key must be declared via `declare(key, type, value, timestamp=None)` before it can be read (`get`) or written (`set(key, value, timestamp=None)`) — `set()` raises if the key wasn't declared or the value isn't an instance of its declared type, which is what lets Backseater reject a Frontseater trying to write a wrong-typed output. `declare()` is callable at any time, not just at construction from a mission graph's `"knowledge"` section, since a running capability can declare a brand-new key mid-execution. `timestamp` defaults to wall-clock time if omitted and is retrievable via `timestamp_of(key)` — this is what a pairwise mesh sync compares across platforms for last-write-wins. `set_or_declare(key, value, timestamp=None)` behaves like `set()` for an already-declared key, otherwise auto-declares via `type(value)` — the rarely-needed bypass mesh sync uses to push a fact a platform's mission graph never pre-declared. Values need not be `KnowledgeEntry` subclasses — plain types (`bool`, `float`, ...) work the same way as object types like `Location`. `KnowledgeEntry` remains the base for richer object types and still requires `describe()` (ABC-enforced, mirroring `Capability`/`ParamSpec`'s self-description); `Location` is the only built-in entry type so far. `Knowledge.all()` returns every entry regardless of type — the query path a visualization tool uses to browse a platform's full knowledge.

**Condition** (`condition/condition.py`): mission graph edge conditions are a pre-tokenized boolean expression over Knowledge keys — e.g. `["(", "ugv1/arrived", "==", True, "and", "ugv1/battery", ">", 0.9, ")", "or", "ugv1/target_found", "is", "not", None]` — parsed once (`parse_condition()`) by a recursive-descent parser into a small typed tree (`Comparison`, `IsNone`, `And`, `Or`, `Not`, each with `evaluate(knowledge)`), not via `eval()` or string parsing of literals: token values (`True`/`None`/numbers) are already real Python objects in the list, only keys/operators/keywords/parens are strings. Standard precedence (`not` > `and` > `or`, parens override). This replaced an earlier `{"primitive": idx, "status": "success"}` schema — primitive status no longer drives transitions at all; a capability decides for itself what to write to Knowledge and when (e.g. `move_to` writes `arrived` on every poll, resettable to `False` when given a new target; `avoid` writes `registered` once live, since "success" has no real meaning for an instantaneous action).

**Visualization** (`viz/`): `EnvironmentViewer` (`viz/base.py`) is the ABC an environment's spatial viewer implements — `configure_ax`/`render` draw onto a matplotlib `Axes` the viewer doesn't own, so it can be embedded rather than owning its own window. Each environment provides its own viewer under `world/<environment_name>/viz/` (e.g. `world/ground_plane/viz/plane_plotter.py`'s `PlanePlotter`), mirroring the Frontseater/Hardware per-environment split. `MissionGraphViewer` (`viz/mission_graph_view.py`) draws a mission graph (active node highlighted, hover for details) onto an `Axes` the same way, laid out via `compute_graph_layout()` — a deterministic force-directed (Fruchterman-Reingold-style) layout, not a columnar one, so a cycle's nodes spread into a polygon (e.g. a triangle for 3 nodes) instead of a straight row whose cycle-closing edge would have to curve around intervening nodes. Each edge's arrowhead is drawn at its midpoint rather than at the target node's coordinates — an arrowhead placed exactly at the target would render underneath that node's marker (drawn afterward, on top) and be invisible. Hover hit-testing happens in display (pixel) space rather than data space, since node/edge markers are a fixed size in points regardless of the current view — a data-unit tolerance would drift out of sync with the actual on-screen marker size across window resizes, pans, and zooms. All hover tooltips (node/edge/platform) lead with a `"Node: "`/`"Edge: "`/`"Platform: "` title line and a separator rather than raw data. `PlatformOverviewViewer` (`viz/platform_overview_view.py`) draws one row per platform id the same way, for the dashboard's "Mission Overview" entry: each row always shows `platform_id: "active_node_id"` inline (not just on hover) next to a small colored box marking the hover/click target, with the fuller active-primitives detail still reserved for hover. `MissionDashboard` (`viz/dashboard.py`) is the top-level Tkinter tool: a platform dropdown (defaulting to its extra "Mission Overview" entry, not the first platform), the embedded `EnvironmentViewer`, a "Mission Overview" panel (titled that regardless of what it's currently showing), and a combined capability-status/knowledge panel (defaulting to Knowledge, not Capabilities) switched by a selector — platform- and environment-agnostic, driven only through `World`/`Backseater`/`Knowledge`/`Relay`'s public query methods. Selecting "Mission Overview" swaps the mission graph for `PlatformOverviewViewer` (hover shows each platform's active primitives; left-clicking a row selects that platform, same as picking it from the dropdown) and the knowledge panel's source from a single platform's `Knowledge` to `Relay.all()`, if a `Relay` is attached to the `World`; the "Show edge labels" checkbox and a "back to overview" button only make sense for — and are only shown for — a single selected platform's own mission graph, hidden again once back in Mission Overview. The knowledge panel's columns are ordered Name/Type/Value (Name and Type narrower than Value, sized to fit without resizing on startup). It also owns the sim's pause state (`is_paused()`), which `main.py`'s loop checks before calling `world.step()`.

## Local LLM (mission-commander)

The mission-commander LLM runs locally via Ollama on `qwen3.5:4b`, CPU-only, no cloud API — see `docs/llm_setup.md` for setup/usage and `notes.md` (13 Aug 26 entry) for rationale. `llm/ollama/` holds the start/stop scripts and `llm_config.yaml` (model name, system prompt, generation params as plain data, not yet loaded by any Python code). Status: scripts/config/docs only — no Python `/api/chat` client, no streaming, no agentic tool-call loop, no eval against the mission-graph tool schema yet.

## Remaining build order (from `notes.md`)

Status: steps 1–2 done (knowledge-based edge conditions/capability outputs, and a narrow structural validation that `World`/`Backseater`/viz already support multiple independent platforms). Step 3 (the centralized `Relay`) was built and tested, then superseded by the 19 Aug 26 peer-to-peer mesh redesign — see `notes.md` — which folds Relay's job into Backseater/World as described in the architecture section above. That redesign is now the current step 3, not yet implemented. The Foreman/Frontend/MissionBuilder ideas from earlier sessions are dropped/deferred per that same redesign; no LLM-facing graph-authoring surface is being built yet.

3. Peer-to-peer mesh redesign, scoped into six increments (each independently implemented/tested before the next starts):
   1. **Data model** — add `Mission`/`Capabilities`/`Status` database classes on `Backseater` alongside the existing `Knowledge`; retrofit `origin_platform_id` onto all four. No cross-platform behavior yet.
   2. **Privilege hierarchy + gated Mission writes** — privilege level assigned at construction; Mission writes gated by privilege check (skipped entirely for a platform writing its own Mission entry — the stated rule only governs writing *another* platform's entry) + type check + structural verify.
   3. **Hot-swap** — a successful Mission write re-declares the new graph's knowledge keys, cancels in-flight capabilities from the old graph, and jumps the active node to the new start node. Testable via direct Mission-write calls, no networking yet.
   4. **Continuous `query()`/`publish()` + capability migration (combined)** — add the capability-facing `query()`/`publish()`/declare-new-key methods on `Backseater`; downgrade `ParamSpec` to key+type+description; migrate the existing capabilities (`move_to`, `avoid`) onto the new methods and remove the old static resolve-then-execute path in the same pass (decided against a coexistence period, to keep the diff self-contained).
   5. **Pairwise `sync_with()` + repurposed Clock** — port the old Relay's pull/push/last-write-wins logic into a `Backseater`-to-`Backseater` method generalized across all four databases; add the per-peer clock-offset handshake as part of `sync_with()`. Tested with two `Backseater`s directly, no `World` involved.
   6. **World integration + cleanup** — `World.step()` drives pairwise `sync_with()` across every pair of `Backseater`s it holds, replacing `relay.sync()`; delete `relay/relay.py` and its dedicated tests; update `main.py`/`missions.py` wiring; end-to-end mesh integration test analogous to today's `test_relay_mission_integration.py`.
4. Mission-authoring surface (an interactive capability/Frontseater replacing the earlier MissionBuilder sketch) + LLM/operator "interface" platform — deferred out of step 3, no LLM yet, fully testable without one.
5. Real comms boundary with simulated delay, planner↔backseater and backseater↔frontseater. Make `poll_status` able to actually return `"timeout"`; make mesh connectivity in step 3 actually partial/topological rather than always-fully-connected.
6. Staleness/timeout semantics on mission-graph edge conditions.
7. True concurrent active nodes (not just concurrent primitives within one node).
8. Cross-platform dependent edges + reconciliation on reconnect; comms-blackout stress test.
9. Object/world-state/OPORD layer (object lists, confidence, OPORD parsing) — lowest priority.

Tests land alongside each step above, in `tests/` (stdlib `unittest` — no test framework dependency added; pytest is not installed).

## Process

For any non-trivial feature or change (not one-line fixes):

1. **Interview first.** Ask clarifying questions throughout — before planning, and again whenever a decision comes up mid-implementation that the user hasn't already settled (e.g. naming, scope, library choices). Don't guess on ambiguous or high-blast-radius decisions.  Use a live task list to track the planning process.
2. **Plan, then get approval before writing code.** Produce a live task list of the concrete implementation steps, then summarize the proposed changes and wait for explicit approval/discussion before implementing anything.
3. **Implement incrementally**, checking items off the plan as they land.
4. **Test as you go, not after.** Write unit tests alongside each change, not as a separate deferred phase.
5. **Backfill missing coverage.** While touching a file, also add tests for previously-untested code nearby if it has none — pick a reasonable strategy for how much to cover (this project has no fixed rule for "how many tests," so judge case by case) rather than asking each time.
6. **Verify before handing back.** Run the full test suite and do a smoke test of the actual behavior (not just "tests pass") before reporting anything as done.
7. **Stop and wait for feedback** at the end of a batch of changes rather than continuing on to unrequested follow-on work.

## Coding style

- **No abbreviations in identifiers** — `environment` not `env`, `hardware_instance` not `hw`, `distance` not `dist`. Full words even when a term is used constantly. (Exception: pre-existing math/physics conventions like `dt`, `vx`, `vy`, `vtheta` stay as-is.)
- Module docstring is a single line: `"""Defines a world"""`.
- Class docstrings are 1–3 sentences; give a very brief overview of what something does, what the interface to work with it is, and any major *why* decisions.
- Docstrings on every function, primarily 1 line.
- Inline comments justify non-obvious decisions (`# persistent, not a task`, `# warm-start cache`), never restate the code.
- Type hints on public method signatures and dataclass-like fields; not enforced everywhere, not obsessive.
- ABCs (`abc.ABC`/`@abstractmethod`) define the layer interfaces (`Hardware`, `Frontseater`, `Environment`); concrete platform code lives under `world/<environment_name>/`.
- Debug prints are tagged by layer: `print(f"[Backseater] ...")`, `[Frontseater]`, `[World]`. Each layer takes a `debug: bool = False` constructor flag gating its own prints — off by default; a caller (e.g. `main.py`'s `DEBUG` constant) opts in per layer.
- Separate major sections in files with `#==========# Note #==========#` and major sections in classes/objects/functions with `#=====# Note #=====#`.  For minor sections, replace the `=` with `-`.
