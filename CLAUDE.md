# MTOFR_SIM

Simulator for platform-agnostic mission-type orders. Pure Python (numpy/scipy/matplotlib), no ROS/networking/async libs yet.

## Architecture (see `notes.md` for full history/rationale)

Three layers per platform, strictly one-directional in what each knows about:
- **Higher level planning (formerly planner)** (not built yet) — will write mission graphs, query capabilities via `backseater.capabilities()`.  This layer is broken down into: 
  - **Foreman** (not built yet) — mission graph manager. Owns the multi-platform union view (one active node per assigned platform), handles LLM/user tool calls that edit the graph, runs a **verify** step (checks every edge-condition Knowledge key is declared in the graph — edge-reachability checking deferred), and delegates validated graphs to Backseaters. Verify runs manually and always automatically on issue-order, never on every tool call.
  - **Relay** (`relay/relay.py`) — owns the canonical cross-platform Knowledge database (distinct from each Backseater's own per-platform `Knowledge`) and handles conflict resolution (last-write-wins by timestamp — a placeholder, not robust). `sync(backseaters)`, called by `World.step()` once per tick after dynamics, pulls every platform's current Knowledge into the canonical store (newest timestamp per key wins, gated by a per-platform checksum so an unchanged platform's Knowledge is skipped rather than re-scanned) and pushes any canonical fact newer than a platform's local copy back into that platform's Knowledge via `Knowledge.set_or_declare()` — the rarely-needed bypass a future replanning flow (Frontend/LLM pushing a fact no mission graph anticipated) would use, since normally the receiving platform's own mission graph pre-declares any foreign key it depends on. Clock synchronization is a documented placeholder: `sync_clock()` always resets a platform's `Clock` (`clock/clock.py`, owned by `Backseater`) to offset 0.0 — the real mechanism is still an open design question. This is the "higher-level asset relaying facts across an async comms boundary" referenced below in the build order.
  - **Frontend** (not built yet) — user + LLM-facing layer; the LLM is one component within it, not a peer of Foreman/Relay. Every LLM tool (graph edits, knowledge query/write) is also exposed to the user directly — same methods, multiple callers. Frontend's knowledge writes go through Relay like any platform's would (own identity, same validation/conflict path, no bypass). Dedicated UI deferred; shared method signatures are the near-term deliverable.
- **Backseater** (`backseater/backseater.py`) — platform-agnostic. Holds the mission graph, relays typed capability requests to its Frontseater, never touches physical state. Exposes `capabilities()` as a passthrough to its Frontseater's registry — the real query path a planner uses instead of assuming what a platform can do. Exposes `status()` as a read-only snapshot (active node, blocked flag, per-primitive capability/status/inputs — the static `field_name -> knowledge_key` mapping from the mission graph, not a live-resolved value; a viewer resolves each key itself via `Knowledge.get()`) — the query path a visualization tool uses instead of reaching into private state. Every capability input is a Knowledge key (see below); Backseater resolves each one via `Knowledge.get()` and validates the resolved values against the platform's `Capability` before calling `start_capability()`, halting the mission gracefully (like an unsupported capability) on a bad/unknown key. On every `poll_status()` call — including the same tick a primitive is first started, so a reset output can't stay stale for an extra tick — it also commits any bound capability outputs back to Knowledge via `Knowledge.set()`, type-checked first. Primitive `status` (`waiting`/`success`/`fail`/`timeout`) is comms-health information only; it never drives mission graph transitions. Edges transition on Knowledge-based conditions instead (see below), parsed once at construction and evaluated against current Knowledge each tick. `Backseater` also owns platform identity: an optional `platform_id: str` given at construction is stored on itself and, if given, assigned to `self.frontseater.platform_id` — this is the one place identity is set; it is never set directly on a Frontseater or Hardware instance. `Backseater` also owns an optional `clock: Clock` (defaulting to its own `Clock()`), stamping every `Knowledge.declare()`/`Knowledge.set()` call with `clock.now()` — this is what lets Relay compare two platforms' write times for a given key.
- **Frontseater** (e.g. `world/ground_plane/frontseater.py`) — platform-specific planning/control brain (MPC, capability implementations). Talks to its Hardware only through `send_controls`/`read_state`. Builds its own `CapabilityRegistry` declaratively in `__init__` and returns it from `capabilities()` — there is no separate central capability manifest; a planner learns what a platform can do only by querying that platform's own backseater. Implements `start_capability()`/`poll_status()`/`cancel()`; `poll_status()` returns `{"status": ..., "outputs": {name: value, ...}}` — a capability decides for itself what, if anything, is meaningful to report on a given status (e.g. `move_to` reports its `arrived` output on every poll; `avoid` reports `registered` once its region is live). `Frontseater.platform_id` is a property, not a plain attribute: its setter also assigns `self.hardware.platform_id`, so a Backseater setting the id once on its Frontseater cascades it all the way down to Hardware automatically.
- **Hardware** (e.g. `world/ground_plane/hardware.py`) — MCU/actuator-equivalent. Owns `WorldState`, pure `calculate_dynamics`. `read_state()` goes through a `PerfectSensor` stub — the seam for a future noisy sensor model. Holds a plain `platform_id: str | None` attribute, set only via the Frontseater cascade above — Hardware never sets its own identity.

`World` ticks: `backseater.update()` → `frontseater.update()` → `environment.step_dynamics_all(hardware)` → (if a `Relay` is attached) `relay.sync(backseaters)`. `World` itself is already platform-count-agnostic (its `backseaters` constructor arg is `entity_id -> Backseater`, iterated generically), and so is the viz layer (`MissionDashboard`'s platform dropdown and `PlanePlotter`'s per-entity rendering both iterate `world.backseaters`/`world.get_states()`) — adding another platform is purely a matter of building another independent hardware/frontseater/knowledge/backseater stack and adding it to the `backseaters` dict, with no shared state or coordination between stacks. Cross-platform coordination is explicitly out of scope for Backseater/Frontseater; per the resolved architecture it is the future planner's job, relayed across an async comms boundary (see build order step 7), not something backseaters do directly with each other.

Mission graph shape: `{"knowledge": {key: {"type": type, "value": value}, ...}, "nodes": {id: {"primitives": {name: {"capability", "inputs", "outputs"}}}}, "edges": {id: [{"condition": [token, ...], "to": ...}]}, "start": id}`. The top-level `"knowledge"` section declares every Knowledge key the graph uses (type-locked, seeded with a default `value`) — Backseater seeds `Knowledge` from it at construction. A primitive's `"inputs"`/`"outputs"` dicts map a capability's declared field names to Knowledge keys (never raw literals — see Capability registry below). `"condition"` is a pre-tokenized boolean expression over Knowledge keys (see Condition below). Multiple primitives can be concurrently active *within* one node; only one node is active at a time (not yet a true concurrent automaton — see build order). `missions.py` holds `main.py`'s example mission graph dicts, named `mission_<set>_<platform_id>` (e.g. `mission_split_ugv1`/`mission_split_ugv2` for independent per-platform loops, `mission_wait_ugv1`/`mission_wait_ugv2` for the Relay cross-platform demo), grouped by an exported `MissionSet` IntEnum and imported rather than inlined, so `main.py` stays wiring-only.

**Capability registry** (`capability/capability.py`): `ParamSpec` (name, `type`, plaintext description) — one shape used for both `Capability.inputs` and `Capability.outputs`, since every field, input or output, is always a Knowledge reference; there is no raw-literal path. `Capability` (`ipl_type`, description, `inputs`, `outputs`, `validate_inputs()`, `validate_outputs()`, `describe()`) + `CapabilityRegistry` (keyed by `ipl_type`; `.get()`, `.all()`, `.describe()`). A primitive's `"capability"` field in the mission graph must match a `Capability.ipl_type`, and that same string is what gets passed straight through to `Frontseater.start_capability()` — no separate internal capability name. `ParamSpec.describe()` calls `type.describe()` when `type` is a `KnowledgeEntry` subclass (duck-typed via `hasattr`), and omits it for plain types (`float`, `bool`, ...) which don't implement that contract. The Backseater resolves every input key via `Knowledge.get()` before validating/starting a capability, and commits every bound output via `Knowledge.set()` after validating it against the matching `ParamSpec` in `Capability.outputs`.

**Knowledge** (`knowledge/knowledge.py`): `Knowledge` is a typed, type-locked key -> value store (one instance per backseater, exposed as `backseater.knowledge`). Every key must be declared via `declare(key, type, value, timestamp=None)` before it can be read (`get`) or written (`set(key, value, timestamp=None)`) — `set()` raises if the key wasn't declared or the value isn't an instance of its declared type, which is what lets Backseater reject a Frontseater trying to write a wrong-typed output. `timestamp` defaults to wall-clock time if omitted and is retrievable via `timestamp_of(key)` — this is what Relay compares across platforms for last-write-wins. `set_or_declare(key, value, timestamp=None)` behaves like `set()` for an already-declared key, otherwise auto-declares via `type(value)` — the rarely-needed bypass Relay uses to push a fact a platform's mission graph never pre-declared. Values need not be `KnowledgeEntry` subclasses — plain types (`bool`, `float`, ...) work the same way as object types like `Location`. `KnowledgeEntry` remains the base for richer object types and still requires `describe()` (ABC-enforced, mirroring `Capability`/`ParamSpec`'s self-description); `Location` is the only built-in entry type so far. `Knowledge.all()` returns every entry regardless of type — the query path a visualization tool uses to browse a platform's full knowledge.

**Condition** (`condition/condition.py`): mission graph edge conditions are a pre-tokenized boolean expression over Knowledge keys — e.g. `["(", "ugv1/arrived", "==", True, "and", "ugv1/battery", ">", 0.9, ")", "or", "ugv1/target_found", "is", "not", None]` — parsed once (`parse_condition()`) by a recursive-descent parser into a small typed tree (`Comparison`, `IsNone`, `And`, `Or`, `Not`, each with `evaluate(knowledge)`), not via `eval()` or string parsing of literals: token values (`True`/`None`/numbers) are already real Python objects in the list, only keys/operators/keywords/parens are strings. Standard precedence (`not` > `and` > `or`, parens override). This replaced an earlier `{"primitive": idx, "status": "success"}` schema — primitive status no longer drives transitions at all; a capability decides for itself what to write to Knowledge and when (e.g. `move_to` writes `arrived` on every poll, resettable to `False` when given a new target; `avoid` writes `registered` once live, since "success" has no real meaning for an instantaneous action).

**Visualization** (`viz/`): `EnvironmentViewer` (`viz/base.py`) is the ABC an environment's spatial viewer implements — `configure_ax`/`render` draw onto a matplotlib `Axes` the viewer doesn't own, so it can be embedded rather than owning its own window. Each environment provides its own viewer under `world/<environment_name>/viz/` (e.g. `world/ground_plane/viz/plane_plotter.py`'s `PlanePlotter`), mirroring the Frontseater/Hardware per-environment split. `MissionGraphViewer` (`viz/mission_graph_view.py`) draws a mission graph (active node highlighted, hover for details) onto an `Axes` the same way, laid out via `compute_graph_layout()` — a deterministic force-directed (Fruchterman-Reingold-style) layout, not a columnar one, so a cycle's nodes spread into a polygon (e.g. a triangle for 3 nodes) instead of a straight row whose cycle-closing edge would have to curve around intervening nodes. Each edge's arrowhead is drawn at its midpoint rather than at the target node's coordinates — an arrowhead placed exactly at the target would render underneath that node's marker (drawn afterward, on top) and be invisible. Hover hit-testing happens in display (pixel) space rather than data space, since node/edge markers are a fixed size in points regardless of the current view — a data-unit tolerance would drift out of sync with the actual on-screen marker size across window resizes, pans, and zooms. All hover tooltips (node/edge/platform) lead with a `"Node: "`/`"Edge: "`/`"Platform: "` title line and a separator rather than raw data. `PlatformOverviewViewer` (`viz/platform_overview_view.py`) draws one row per platform id the same way, for the dashboard's "Mission Overview" entry: each row always shows `platform_id: "active_node_id"` inline (not just on hover) next to a small colored box marking the hover/click target, with the fuller active-primitives detail still reserved for hover. `MissionDashboard` (`viz/dashboard.py`) is the top-level Tkinter tool: a platform dropdown (defaulting to its extra "Mission Overview" entry, not the first platform), the embedded `EnvironmentViewer`, a "Mission Overview" panel (titled that regardless of what it's currently showing), and a combined capability-status/knowledge panel (defaulting to Knowledge, not Capabilities) switched by a selector — platform- and environment-agnostic, driven only through `World`/`Backseater`/`Knowledge`/`Relay`'s public query methods. Selecting "Mission Overview" swaps the mission graph for `PlatformOverviewViewer` (hover shows each platform's active primitives; left-clicking a row selects that platform, same as picking it from the dropdown) and the knowledge panel's source from a single platform's `Knowledge` to `Relay.all()`, if a `Relay` is attached to the `World`; the "Show edge labels" checkbox and a "back to overview" button only make sense for — and are only shown for — a single selected platform's own mission graph, hidden again once back in Mission Overview. The knowledge panel's columns are ordered Name/Type/Value (Name and Type narrower than Value, sized to fit without resizing on startup). It also owns the sim's pause state (`is_paused()`), which `main.py`'s loop checks before calling `world.step()`.

## Local LLM (mission-commander)

The mission-commander LLM runs locally via Ollama on `qwen3.5:4b`, CPU-only, no cloud API — see `docs/llm_setup.md` for setup/usage and `notes.md` (13 Aug 26 entry) for rationale. `llm/ollama/` holds the start/stop scripts and `llm_config.yaml` (model name, system prompt, generation params as plain data, not yet loaded by any Python code). Status: scripts/config/docs only — no Python `/api/chat` client, no streaming, no agentic tool-call loop, no eval against the mission-graph tool schema yet.

## Process

For any non-trivial feature or change (not one-line fixes):

1. **Interview first.** Ask clarifying questions throughout — before planning, and again whenever a decision comes up mid-implementation that the user hasn't already settled (e.g. naming, scope, library choices). Don't guess on ambiguous or high-blast-radius decisions.  Use a live task list to track the planning process.
2. **Plan, then get approval before writing code.** Produce a live task list of the concrete implementation steps, then summarize the proposed changes and wait for explicit approval/discussion before implementing anything.
3. **Implement incrementally**, checking items off the plan as they land.
4. **Test as you go, not after.** Write unit tests alongside each change, not as a separate deferred phase.
5. **Backfill missing coverage.** While touching a file, also add tests for previously-untested code nearby if it has none — pick a reasonable strategy for how much to cover (this project has no fixed rule for "how many tests," so judge case by case) rather than asking each time.
6. **Verify before handing back.** Run the full test suite and do a smoke test of the actual behavior (not just "tests pass") before reporting anything as done.
7. **Stop and wait for feedback** at the end of a batch of changes rather than continuing on to unrequested follow-on work.

## Coding style

- **No abbreviations in identifiers** — `environment` not `env`, `hardware_instance` not `hw`, `distance` not `dist`. Full words even when a term is used constantly. (Exception: pre-existing math/physics conventions like `dt`, `vx`, `vy`, `vtheta` stay as-is.)
- Module docstring is a single line: `"""Defines a world"""`.
- Class docstrings are 1–3 sentences; give a very brief overview of what something does, what the interface to work with it is, and any major *why* decisions.
- Docstrings on every function, primarily 1 line.
- Inline comments justify non-obvious decisions (`# persistent, not a task`, `# warm-start cache`), never restate the code.
- Type hints on public method signatures and dataclass-like fields; not enforced everywhere, not obsessive.
- ABCs (`abc.ABC`/`@abstractmethod`) define the layer interfaces (`Hardware`, `Frontseater`, `Environment`); concrete platform code lives under `world/<environment_name>/`.
- Debug prints are tagged by layer: `print(f"[Backseater] ...")`, `[Frontseater]`, `[World]`. Each layer takes a `debug: bool = False` constructor flag gating its own prints — off by default; a caller (e.g. `main.py`'s `DEBUG` constant) opts in per layer.
- Separate major sections in files with `#==========# Note #==========#` and major sections in classes/objects/functions with `#=====# Note #=====#`.  For minor sections, replace the `=` with `-`.
