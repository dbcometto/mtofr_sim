# MTOFR_SIM

Simulator for platform-agnostic mission-type orders. Pure Python (numpy/scipy/matplotlib), no ROS/networking/async libs yet.

Experiment plan: Just like SSRR, compare human teleoperation (convoy system?) to autonomy for logistics tasks, in sim and in hardware.  Human commander is responsible for accomplishing a variety of pick-up/drop-off missions that arrive in a scripted manner, and task performance is measured (in various ways) and analyzed.  Simulator will be able to have more powerful analysis tools (likely), but a hardware demo would reinforce.

## Architecture (see `notes.md` for full history/rationale)

Per-platform layers, redesigned as fully peer-to-peer/mesh (see `notes.md`'s 19 Aug 26 entry for the full rationale; supersedes the earlier centralized Foreman/Relay/Frontend design and the four-relay/MissionBuilder sketch that followed it — neither was built, both are marked superseded in `notes.md` rather than deleted):

- **Backseater** (`backseater/backseater.py`) — platform-agnostic. Holds the mission graph, relays typed capability requests to its Frontseater, never touches physical state. Exposes `capabilities()` as a passthrough to its Frontseater's registry — the real query path a planner uses instead of assuming what a platform can do. Exposes `status()` as a read-only snapshot (active node, blocked flag, per-primitive capability/status/inputs — the static `field_name -> knowledge_key` mapping from the mission graph, not a live-resolved value). `Backseater` owns platform identity exactly as before: an optional `platform_id: str` given at construction cascades to `self.frontseater.platform_id` — the one place identity is set. `Backseater` also owns an optional `clock: Clock`, now stamping every write across all three databases below (not just Knowledge).

  **Three databases per platform, all owned by Backseater** — `KnowledgeDatabase`/`MissionDatabase`/`PlatformDatabase`, all named consistently as `<Concept>Database` and all retrofitted with `origin_platform_id` tracking (increment 1, done — see build order). `PlatformDatabase` merges what were originally sketched as separate Capabilities and Status databases into a single gossiped-per-platform record, decided during increment 2 once privilege level needed a home too — one row per known platform instead of three:
  - **Knowledge** (`KnowledgeDatabase`, in `database/knowledge.py`, exposed as `backseater.knowledge_database`; its entry types — `KnowledgeEntry`, `Location` — live in `database/knowledge_types.py`) — arbitrary entry keys (not platform_id-keyed), strongly typed per key via `declare()`/`declare_key()`. Declaration is now callable by a Frontseater/capability at any time, not only seeded once from the mission graph's `"knowledge"` section at construction — ordinary type/existence checking still applies on every write.
  - **Mission** (`MissionDatabase`, in `database/platform_keyed.py`, exposed as `backseater.mission_database`) — keyed by platform_id, one `mission_graph` value per platform, type-locked to `dict`. `Backseater.write_mission(mission_graph, writer_platform_id, timestamp=None)` (increment 2, done) is the single gated write point a write from another platform must go through: a privilege check (see below, skipped entirely when `writer_platform_id` is this platform's own id), a type check, and a structural verify (`database.verify_mission_structure()` — every edge-condition key referenced in the graph must be declared in that graph's own `"knowledge"` section, raising `MissionStructuralError`, a `ValueError` subclass, on failure — edge-reachability checking still deferred). Direct `declare()`/`set()` calls on the database itself remain unrestricted, used for a platform's own self-writes. A successful write does not yet trigger hot-swap — that's increment 3.
  - **Platform** (`PlatformDatabase`, in `database/platform_keyed.py`, exposed as `backseater.platform_database`) — keyed by platform_id, one `PlatformRecord(privilege_level, status, capabilities)` per platform, type-locked to `PlatformRecord`. `status` (`PlatformStatus(status, message)`, defaulting to `PlatformStatus("idle")`) and `capabilities` (a gossiped `CapabilityRegistry` snapshot, defaulting to `None` until a Frontseater populates it) are self-write-only once mesh sync exists, but that restriction isn't enforced yet (no mesh sync). `privilege_level` is never self-write-only, even once sync exists — only a strictly higher-privilege platform may change it (see below); a Backseater seeds its own record at construction from its `privilege_level` constructor arg (default `1`; `0` is reserved). This is also the lookup `write_mission()` uses to resolve both sides' privilege levels for the Mission-write gate. Distinct from `Backseater.status()`, the pre-existing local read-only mission-progress snapshot method, which is unchanged.

  A running capability is no longer resolve-then-execute (increment 4, done): while active it can `query()`/`publish()` (or `declare_knowledge_key()` for a brand-new key) through its own Backseater at any time — reached via `frontseater.backseater`, set by `Backseater.__init__` right after `self.frontseater` is stored, mirroring the `platform_id` cascade — against any of the three databases above, instead of only receiving resolved input values once at start. `query(database_name, key)`/`publish(database_name, key, value, timestamp=None)` are generalized across all three databases via a `database_name` string (`"knowledge"`/`"mission"`/`"platform"`); a `"mission"` publish always routes through the gated `write_mission()` rather than writing `mission_database` directly, since Mission has exactly one entry per platform and a capability publishing to it is always a self-write. Backseater remains the sole thing enabling/disabling capabilities; Frontseater remains the sole thing executing them — this relationship is unchanged, just richer in its data flow. Type-safety is centralized in two places rather than left to each Frontseater implementation: each database's own `set()` still rejects a mistyped write at query/publish time, and `Backseater._check_binding_types()` runs once, at bind time (right before a capability is started), verifying that every Knowledge key a primitive binds to one of that capability's declared input/output fields is itself declared with that field's exact `ParamSpec` type — catching a mismatched or undeclared key before the capability ever runs, the same way eager resolve-then-execute used to.

  Every entry across all three databases carries an `origin_platform_id` — the platform that held it at its most recently locally-converted timestamp, transitively — alongside its value/timestamp; this is what privilege checks key off of.

  **Privilege hierarchy** (increment 2, done): each platform is assigned an integer privilege level (0 = highest, 1 = default) by the simulation harness at construction via `Backseater`'s `privilege_level` constructor arg. A platform may write another platform's Mission database entry only if its own level is strictly higher-privilege (lower number) than the target's; an unknown writer (no `PlatformRecord` yet known for it) is rejected the same way, with `PermissionError`. Runtime *reassignment* of another platform's privilege level ("it may only assign levels less-or-equal to its own, and can never modify its own level") is specified but **explicitly deferred** — no method for it exists yet; it's added whenever it's actually needed, likely alongside real mesh sync in increment 5.

  **Hot-swap**: when a Backseater detects its own Mission database entry has changed, it declares/sets every knowledge key listed in the new graph's `"knowledge"` section, cancels every currently-running capability from the old graph, sets the active node to the new graph's declared start node, and starts that node's capabilities.

  All type/privilege/structural checks happen write-side only, once, at the originating platform's `publish()` call — there is no receipt-side re-verification; the network is assumed correct downstream of a valid write.

- **Frontseater** (e.g. `world/ground_plane/frontseater.py`) — platform-specific planning/control brain (MPC, capability implementations). Talks to its Hardware only through `send_controls`/`read_state`. Builds its own `CapabilityRegistry` declaratively in `__init__` and returns it from `capabilities()` — there is no separate central capability manifest; a planner learns what a platform can do only by querying that platform's own backseater. Implements `start_capability(capability, inputs, outputs)`/`poll_status()`/`cancel()`, where `inputs`/`outputs` are field-name -> Knowledge-key maps (the mission graph's initial binding), not resolved values; a capability calls `query()`/`publish()` on its own Backseater (reached via its `backseater` attribute, set by `Backseater.__init__`) whenever it actually needs data, for any of the three databases, rather than only being handed resolved input values at start — e.g. `BicycleFrontseater.move_to` re-queries its bound `target`/`tolerance` keys on every `poll_status()` call (so a mid-flight retarget takes effect on the next poll), while `avoid` queries its `point`/`radius` keys once since it's instantaneous; `stopwatch` takes no inputs at all and reports simulation seconds elapsed (via `WorldState.t`) since it was last started, never completing on its own. All three publish their outputs (`arrived`/`registered`/`elapsed_time`) directly via `publish()` rather than returning them for Backseater to commit. `poll_status()` still returns `{"status": ..., "outputs": {name: value, ...}}`, now read-only reporting rather than a write path, for whatever a capability decides is meaningful to report on a given status. `Frontseater.platform_id` is a property whose setter also assigns `self.hardware.platform_id`, cascading a Backseater-assigned id all the way down to Hardware automatically.
- **Hardware** (e.g. `world/ground_plane/hardware.py`) — unchanged by this redesign: MCU/actuator-equivalent, owns `WorldState`, pure `calculate_dynamics`, `read_state()` through a `PerfectSensor` stub, holds a plain `platform_id: str | None` attribute set only via the Frontseater cascade.

There is no centralized Relay. `World` drives the mesh sync itself — since it's the one thing already holding every platform's Backseater — rather than delegating to a separate Relay object. `World` ticks: `backseater.update()` → `frontseater.update()` → `environment.step_dynamics_all(hardware)` → a pairwise mesh sync between every pair of Backseaters (full connectivity assumed for now; real comms topology/partial connectivity explicitly deferred). World owns *who can currently talk to whom*; Backseater owns *what a sync actually does* once two platforms are paired, via a `sync_with()`-style method absorbing what the old Relay class used to do: pulling/pushing all three databases, last-write-wins by (locally-converted) timestamp — a named simplification, not a robust consensus mechanism. `World` itself remains platform-count-agnostic, and so does the viz layer (`MissionDashboard`'s platform dropdown and `PlanePlotter`'s per-entity rendering both iterate `world.backseaters`/`world.get_states()`); adding another platform is still purely a matter of building another independent hardware/frontseater/backseater stack and adding it to the `backseaters` dict, with no shared state required between stacks beyond what mesh sync itself provides. Cross-platform *coordination* (cross-graph reasoning) remains out of scope for Backseater/Frontseater — only cross-graph *inspection* belongs in a future planner/visualizer — but cross-platform *data propagation* is now peer-to-peer rather than routed through a central component.

Clock (`clock/clock.py`) is repurposed rather than dropped: still owned by Backseater, but instead of one global offset reset to 0.0 by a central Relay, each pairwise `sync_with()` handshake estimates a clock offset to that specific peer, and every incoming fact's timestamp is converted into the receiving platform's own local clock frame immediately and re-stamped in local time before storage — there is no shared/authoritative clock anywhere.

Default startup mission: every platform starts on a hardcoded default mission graph at init (e.g. an idle/loiter loop for an ordinary platform). An eventual LLM/operator "interface" platform (architecturally just another platform, no special class, with a single node running all its own capabilities concurrently under an unconditional self-transition) and any mission-authoring surface for building/editing a graph before publishing it (an interactive capability/Frontseater, replacing the earlier MissionBuilder sketch) are explicitly **deferred to a future step** — not part of this redesign.

Mission graph shape: `{"knowledge": {key: {"type": type, "value": value}, ...}, "nodes": {id: {"primitives": {name: {"capability", "inputs", "outputs"}}}}, "edges": {id: [{"condition": [token, ...], "to": ...}]}, "start": id}`, unchanged in shape by this redesign. The top-level `"knowledge"` section declares every Knowledge key the graph uses (type-locked, seeded with a default `value`) — Backseater seeds `Knowledge` from it both at construction (the hardcoded default mission) and on every subsequent hot-swap (a new value written to that platform's Mission database entry). A primitive's `"inputs"`/`"outputs"` dicts map a capability's declared field names to Knowledge keys (never raw literals — see Capability registry below); with a running capability now able to `query()`/`publish()` at will, these static maps are the *initial* binding a mission graph hands a capability, not the only data it will ever see. `"condition"` is a pre-tokenized boolean expression over Knowledge keys (see Condition below). Multiple primitives can be concurrently active *within* one node; only one node is active at a time (not yet a true concurrent automaton — see build order). `missions.py` holds `main.py`'s example mission graph dicts, named `mission_<set>_<platform_id>`, grouped by an exported `MissionSet` IntEnum. Each `MissionSet` maps (via the `MISSION_SETS` dict) to one `MissionSetConfig` dataclass bundling everything `main.py` needs to wire that set up: `map_name` (a `mtofr.maps` name, or `None` for the fully unbounded mapless mode), `platform_builders` (`platform_id -> Callable[[bool], Frontseater]` — hardware/frontseater construction, including each platform's starting `WorldState`, lives here per mission set rather than in `main.py`, since a different mission set may want different platform types/hardware configs, not just `BicycleHardware`), and `mission_graphs` (`platform_id -> mission graph dict`). `main.py` loops over `mission_set.platform_builders.items()` to build each platform's stack, rather than a fixed number of hardcoded per-platform blocks — `main.py` stays wiring-only and platform-count-agnostic, matching `World`'s own platform-count-agnostic design.

**Capability registry** (`capability/capability.py`): `ParamSpec` carries just a key name plus a declared type (plus plaintext description) — used only for `capabilities()`'s self-description (so a human or LLM can understand what a capability needs by reading its description) and for `Backseater._check_binding_types()`'s bind-time type check (see above); it plays no role in eager value-resolution, since there is none anymore. `Capability` (`ipl_type`, description, `inputs`, `outputs`, `describe()`) + `CapabilityRegistry` (keyed by `ipl_type`; `.get()`, `.all()`, `.describe()`) — `Capability` has no `validate_inputs()`/`validate_outputs()` methods (removed in increment 4; nothing called them once a capability's inputs/outputs stopped being eagerly resolved/committed by Backseater). A primitive's `"capability"` field in the mission graph must match a `Capability.ipl_type`, and that same string is what gets passed straight through to `Frontseater.start_capability()` — no separate internal capability name. `ParamSpec.describe()` calls `type.describe()` when `type` is a `KnowledgeEntry` subclass (duck-typed via `hasattr`), and omits it for plain types (`float`, `bool`, ...) which don't implement that contract. A capability is handed keys, not resolved values, and calls `query()`/`publish()` on its own Backseater whenever it actually needs data, against any of the three databases.

**Knowledge** (`database/knowledge.py`, entry types in `database/knowledge_types.py`): `KnowledgeDatabase` is a typed, type-locked key -> value store (one instance per backseater, exposed as `backseater.knowledge_database`) — one of Backseater's three databases (see architecture above; `MissionDatabase`/`PlatformDatabase`, in `database/platform_keyed.py`, are platform_id-keyed siblings sharing a `PlatformKeyedDatabase` base, each locked to a single fixed value type instead of a per-key type). `database/__init__.py` re-exports everything from all three files, so callers import from `mtofr.database` regardless of which file a class actually lives in. Every key must be declared via `declare(key, type, value, timestamp=None, origin_platform_id=None)` before it can be read (`get`) or written (`set(key, value, timestamp=None, origin_platform_id=None)`) — `set()` raises if the key wasn't declared or the value isn't an instance of its declared type, which is what lets Backseater reject a Frontseater trying to write a wrong-typed output. `declare()` is callable at any time, not just at construction from a mission graph's `"knowledge"` section, since a running capability can declare a brand-new key mid-execution. `timestamp` defaults to wall-clock time if omitted and is retrievable via `timestamp_of(key)` — this is what a pairwise mesh sync compares across platforms for last-write-wins. `origin_platform_id` defaults to `None` and is retrievable via `origin_of(key)` — the platform that held this entry at its most recently locally-converted timestamp, transitively; not yet written by anything other than an explicit caller (increment 1 only adds the storage/accessor, not the privilege checks that will key off it). `set_or_declare(key, value, timestamp=None, origin_platform_id=None)` behaves like `set()` for an already-declared key, otherwise auto-declares via `type(value)` — the rarely-needed bypass mesh sync uses to push a fact a platform's mission graph never pre-declared. Values need not be `KnowledgeEntry` subclasses — plain types (`bool`, `float`, ...) work the same way as object types like `Location`. `KnowledgeEntry` remains the base for richer object types and still requires `describe()` (ABC-enforced, mirroring `Capability`/`ParamSpec`'s self-description); `Location` is the only built-in entry type so far. `KnowledgeDatabase.all()` returns every entry regardless of type — the query path a visualization tool uses to browse a platform's full knowledge.

**Condition** (`condition/condition.py`): mission graph edge conditions are a pre-tokenized boolean expression over Knowledge keys — e.g. `["(", "ugv1/arrived", "==", True, "and", "ugv1/battery", ">", 0.9, ")", "or", "ugv1/target_found", "is", "not", None]` — parsed once (`parse_condition()`) by a recursive-descent parser into a small typed tree (`Comparison`, `IsNone`, `And`, `Or`, `Not`, each with `evaluate(knowledge)`), not via `eval()` or string parsing of literals: token values (`True`/`None`/numbers) are already real Python objects in the list, only keys/operators/keywords/parens are strings. Standard precedence (`not` > `and` > `or`, parens override). This replaced an earlier `{"primitive": idx, "status": "success"}` schema — primitive status no longer drives transitions at all; a capability decides for itself what to write to Knowledge and when (e.g. `move_to` writes `arrived` on every poll, resettable to `False` when given a new target; `avoid` writes `registered` once live, since "success" has no real meaning for an instantaneous action; `stopwatch` writes `elapsed_time` — simulation seconds, via `WorldState.t`, since this capability instance was last (re)started — on every poll, useful for e.g. giving up on a stuck task after a max duration).

**Maps** (`maps/`, sibling to `world/`/`database/`/`viz/`/etc. — not ground_plane-specific, so a future environment could reuse the same map format): `GroundMap` (`maps/ground_map.py`) loads a map directory's yaml plus its cosmetic/traversability/regions PNGs. World coordinates are centered on the map (`(0, 0)` = image center) with `+y` up, matching the bicycle model's own math convention — the opposite of image row order, so pixel sampling flips vertically. The yaml's `traversability` section maps a hex color to a `TraversabilityType(name, blocking, speed_multiplier)`; a sampled pixel color snaps to its *nearest* declared color (by squared RGB distance) rather than requiring an exact match, since PNG anti-aliasing blends a few pixels along every color boundary — an in-bounds unmatched color falls back to a passable/no-effect default, off-map coordinates count as blocked. The `regions` section (`RegionType(name, center_x, center_y)`) is currently display-only — no functional region-membership query exists yet, that's deferred to the logistics build-order step. `GroundPlaneEnv` (`world/ground_plane/env.py`) takes an optional `ground_map` (`None` = fully unbounded, no-effect mapless mode); each tick, before stepping a hardware instance, it samples the map's speed_multiplier at that hardware's *current* position and passes it through to `Hardware.calculate_dynamics()`/`step_dynamics()` (both gained a `max_speed_multiplier: float = 1.0` parameter, a no-op default for any `Hardware` with no such concept) to scale `BicycleHardware`'s own `max_speed`; if the resulting new position is blocked, it reverts to the previous position/heading with velocity zeroed instead of applying the step (an approximate "stop at the boundary," not an exact geometric boundary crossing — fine at the map's raster resolution). The MPC planner itself (`world/ground_plane/mpc.py`) has no notion of this terrain at all — see Future steps.

**Visualization** (`viz/`): `EnvironmentViewer` (`viz/base.py`) is the ABC an environment's spatial viewer implements — `configure_ax`/`render` draw onto a matplotlib `Axes` the viewer doesn't own, so it can be embedded rather than owning its own window; `render()` also takes `show_traversability`/`show_regions` (default `False`, ignored by a viewer with no map) and the class exposes a `background_color` attribute (default `"white"`) that `MissionDashboard` applies to the Axes before each render. Each environment provides its own viewer under `world/<environment_name>/viz/` (e.g. `world/ground_plane/viz/plane_plotter.py`'s `PlanePlotter`), mirroring the Frontseater/Hardware per-environment split. `PlanePlotter` draws each platform as a dot (selected one larger/differently colored) plus a small rotated-triangle heading marker at a fixed on-screen (points) offset from the dot — computed fresh each render via `ax.transData`, so (like the dot's own `markersize`) it stays a constant on-screen size across zoom levels, rather than an `ax.arrow()`'s data-space patch scaling with the current view. Given a `GroundMap`, it also draws the map's cosmetic image (always) plus toggleable traversability/regions overlays (alpha-blended) at the map's world-meters extent, with a combined legend covering both platforms and whichever overlay(s) are visible, and overrides `background_color` to a light gray so panning/zooming past the map's edge reads as "off the map." `MissionGraphViewer` (`viz/mission_graph_view.py`) draws a mission graph (active node highlighted, hover for details) onto an `Axes` the same way, laid out via `compute_graph_layout()` — a deterministic force-directed (Fruchterman-Reingold-style) layout, not a columnar one, so a cycle's nodes spread into a polygon (e.g. a triangle for 3 nodes) instead of a straight row whose cycle-closing edge would have to curve around intervening nodes. Each edge's arrowhead is drawn at its midpoint rather than at the target node's coordinates — an arrowhead placed exactly at the target would render underneath that node's marker (drawn afterward, on top) and be invisible. Hover hit-testing happens in display (pixel) space rather than data space, since node/edge markers are a fixed size in points regardless of the current view — a data-unit tolerance would drift out of sync with the actual on-screen marker size across window resizes, pans, and zooms. All hover tooltips (node/edge/platform) lead with a `"Node: "`/`"Edge: "`/`"Platform: "` title line and a separator rather than raw data. `PlatformOverviewViewer` (`viz/platform_overview_view.py`) draws one row per platform id the same way, for the dashboard's "Mission Overview" entry: each row always shows `platform_id: "active_node_id"` inline (not just on hover) next to a small colored box marking the hover/click target, with the fuller active-primitives detail still reserved for hover. `MissionDashboard` (`viz/dashboard.py`) is the top-level Tkinter tool: a platform dropdown (defaulting to its extra "Mission Overview" entry, not the first platform), the embedded `EnvironmentViewer` (its figure's subplot margins tightened, so the map view fills most of the panel rather than leaving default matplotlib whitespace), two checkboxes above it ("Show traversability"/"Show regions", unchecked by default, ignored by a mapless viewer), a "Mission Overview" panel (titled that regardless of what it's currently showing), and a combined capability-status/knowledge panel (defaulting to Knowledge, not Capabilities) switched by a selector — platform- and environment-agnostic, driven only through `World`/`Backseater`/`Knowledge`'s public query methods. Scroll-wheel zoom and left-click-drag pan work directly on the environment plot (bound via `mpl_connect`), without needing `NavigationToolbar2Tk`'s own pan/zoom-rectangle tools toggled on first — the toolbar itself is kept for Home/Save. Selecting "Mission Overview" swaps the mission graph for `PlatformOverviewViewer` (hover shows each platform's active primitives; left-clicking a row selects that platform, same as picking it from the dropdown); its knowledge panel is left empty, since there is no longer a single canonical cross-platform store to show (each platform's Knowledge is peer-to-peer mesh-synced instead — see below). The "Show edge labels" checkbox and a "back to overview" button only make sense for — and are only shown for — a single selected platform's own mission graph, hidden again once back in Mission Overview. The knowledge panel's columns are ordered Name/Type/Value (Name and Type narrower than Value, sized to fit without resizing on startup). It also owns the sim's pause state (`is_paused()`), which `main.py`'s loop checks before calling `world.step()`.

## Process

For any non-trivial feature or change (not one-line fixes):

1. **Interview first.** Ask clarifying questions throughout — before planning, and again whenever a decision comes up mid-implementation that the user hasn't already settled (e.g. naming, scope, library choices). Don't guess on ambiguous or high-blast-radius decisions.  Use a live task list to track the planning process.
2. **Plan, then get approval before writing code.** Produce a live task list of the concrete implementation steps, then summarize the proposed changes and wait for explicit approval/discussion before implementing anything.
3. **Implement incrementally**, checking items off the plan as they land.
4. **Test as you go, not after.** Write unit tests alongside each change, not as a separate deferred phase.
5. **Backfill missing coverage.** While touching a file, also add tests for previously-untested code nearby if it has none — pick a reasonable strategy for how much to cover (this project has no fixed rule for "how many tests," so judge case by case) rather than asking each time.
6. **Verify before handing back.** Run the full test suite and do a smoke test of the actual behavior (not just "tests pass") before reporting anything as done.
7. **Stop and wait for feedback** at the end of a batch of changes rather than continuing on to unrequested follow-on work.

## Coding style

- **No abbreviations in identifiers** — `environment` not `env`, `hardware_instance` not `hw`, `distance` not `dist`. Full words even when a term is used constantly. (Exception: pre-existing math/physics conventions like `dt`, `vx`, `vy`, `vtheta` stay as-is.)
- Module docstring is a single line: `"""Defines a world"""`.
- Class docstrings are 1–3 sentences; give a very brief overview of what something does, what the interface to work with it is, and any major *why* decisions.
- Docstrings on every function, primarily 1 line.
- Inline comments justify non-obvious decisions (`# persistent, not a task`, `# warm-start cache`), never restate the code.
- Type hints on public method signatures and dataclass-like fields; not enforced everywhere, not obsessive.
- ABCs (`abc.ABC`/`@abstractmethod`) define the layer interfaces (`Hardware`, `Frontseater`, `Environment`); concrete platform code lives under `world/<environment_name>/`.
- Debug prints are tagged by layer: `print(f"[Backseater] ...")`, `[Frontseater]`, `[World]`. Each layer takes a `debug: bool = False` constructor flag gating its own prints — off by default; a caller (e.g. `main.py`'s `DEBUG` constant) opts in per layer.
- Separate major sections in files with `#==========# Note #==========#` and major sections in classes/objects/functions with `#=====# Note #=====#`.  For minor sections, replace the `=` with `-`.
- Any test that constructs a `Frontseater` owning a real OS-level resource (currently only `BicycleFrontseater`'s MPC worker process/queues) must explicitly tear it down — `tearDown()` or `self.addCleanup(frontseater.shutdown)` — rather than relying on `__del__`/garbage collection. `python -m unittest discover` runs the whole suite in one process, where GC-timed cleanup can race between unrelated tests and crash the interpreter outright (see `notes.md`'s 28 Aug 26 entry). Where a helper function builds the stack per-test, have it take the `TestCase` (`self`) as a parameter and register the cleanup itself.
